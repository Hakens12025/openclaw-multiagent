骨架总览 · FC 对象的一生

相位详图 · 四个时刻各一张

T0 · 派工时刻 — contract 诞生与期望注入

现状:contract 带着 task 文本、output 路径、stagePlan 出生,协作要求只活在 task 那句话里。设计:期望字段在此刻凝固——固定管线由平台从图自动导出,动态协作由派工方在 assign_task 参数里顺手填写。

T1 · 会话中 — 每一次 tool call 的守卫、执行与观测扇出

现状病灶:框架交给钩子的事件是完整的(名称/参数/结果/编号俱全),但随即被拆成四份互不相通的内存局部视图,没有任何一份完整、持久、可供考官消费。设计:同一钩子上加一座证据桥,完整正本只记一次。

T2 · agent_end — 提取、选路、消费与终态

现状:文本便条(L2/L3)在提取门后归一消费;固定管线交棒不写便条,由 graph_route 直接把同一份 contract 传给下家;终态链在会话结束时拼判决。设计:提取产物合成为 trace 事件;终态链改读本会话 trace 拿收据索引、查票据账拿现状。

T3 · 轮次审计 — harness、评估与自治决策

现状:EvaluationResult 是 reviewerResult 的原样转贴,harness 各模块只看声明不看行为。设计:考官拿「期望(应然)」对账「trace(实然)」,输出三态判决,真实评估落进原有的决策与信任阶梯,后场一行不改。

⚠ 问题种子②(本轮核查新钉死):role-policy 矩阵里 wake_agent 只有 role="agent" 允许(system-action-role-policy.js:24-50)——executor 角色的 worker 写了便条,也会在死后审时被拒(rolePolicyRejected)。用户这句要求,worker 根本无权执行;而且拒绝发生在会话结束后,worker 生前毫不知情、无法改道。
5

平台翻 worker 的发言稿提取便条(只取第一张);graph_route 纯代码选路:出边 0 条=终点、恰 1 条=自动交棒、≥2 条=歧义,拒绝路由。货检:产物正文 trim 后 <24 字 → contract 判 FAILED(retryable),下家根本不会被唤醒。整条判定链跑在 worker 的会话生命周期里,判的是 worker。

⚠ 问题种子③:现网 worker 实际有两条出边(→worker2 / →reviewer1)——按「恰好一条」规则,自动路由直接判歧义拒走。且用户说的是让 controller 审,图上根本没有 worker→controller 的授权边。用户意图、图拓扑、role 授权三者互相脱节,而系统没有任何环节报告这种脱节。
6

同一份 contract 原地 mutate(assignee=reviewer1),worker 产物整包搬进 reviewer1 的 inbox/upstream/。reviewer1 靠 assignee+task+上游包+自己的 SOUL 知道该干嘛——contract 上没有「你是审查员」字段。

3
平台条件性无处安放

「若发现异常才核查」是条件期望。当前系统里没有任何机制知道「这一轮该不该有 review」——review 发生了,不知道是不是该发生;没发生,更不知道是漏了还是本来就不需要。

4
deferred 回流(带病)request_review 的结果怎么回来 delivery-system-action-transport.js:285-419 → before-agent-start.js:142

走票据登记 → 原契约记 COMPLETED「deferred via」→ 评审 agent 的 agent_end 把结果契约投回源 inbox → exact-session 精确唤醒(3 次确认重试)。链路能走通,但簿记半死:followUpLease 全插件零处启用,resume 全靠 delivery 侧主动唤醒撑着。

当前系统在这两个例子里的六个盲区

  1. 协作期望无字段——「让 controller 审」「叫醒我」只活在自然语言里,机器不可查;
  2. 授权暗坑——role-policy 拒掉 wake_agent,worker 生前无感知、死后无申诉;
  3. 意图与拓扑脱节——用户点名 controller,图上无边;双出边直接歧义拒路由;无人报告;
  4. 多动作单取——第二张便条静默蒸发,四方全盲;
  5. 该叫没叫无人知——全链无任何缺席检测;
  6. 评估空转——EvaluationResult=评审文本转贴,行为证据为零。

FC 大全 · 两个家族分别是干什么的

先对齐术语:「intent(意图)」是系统动作的类型词汇表(protocol-primitives.js 的 INTENT_TYPES,共 7 种),它本身不是工具;协作 FC 就是这些意图的 FC 投影——把「我想叫谁/派谁/请谁审」从文本便条升级成结构化 tool call。与之相对的是 agent 内 FC(干活工具)。两个家族的根本分野在三件事:执行在哪(工具运行时内 vs 平台 consume 代办)、返回什么(执行结果 vs 受理凭证)、谁把关(能力预设/tools.allow vs role-policy+图边)。但在证据面它们完全同形:同一座桥、同一本账。工具面已按「不可替代试金石」(①必须平台代办②现有原语组合不出)收缩定案:v1 只开 3 个协作工具,其余缓建(灰显行),缓建各自标明「等什么再开」。另外两件原挂在协作表里的工具其实不跨 agent——单列为家族三「平台服务 FC」。

家族一 · agent 内 FC(执行面 · 干活工具)

执行发生在工具运行时内部,返回的就是结果本身。平台不代办任何事,只(设计后)记账。

工具干什么执行在哪入账摘要(设计后)
read阅读文件工具运行时{path, bytes}
write / edit / apply_patch写入 / 编辑 / 应用补丁工具运行时{path, bytes, contentHash}——产物目击的来源
bash / exec执行命令工具运行时{命令前200字, exitCode}
glob / grep检索文件 / 内容工具运行时{pattern}
web_search / web_fetch搜索 / 读网页工具运行时(经能力门){query / host}

sessions_send跨会话发消息——边界特例:形态是内部工具,效果却跨 agent;当前被 after_tool_call 特判记派工链(hooks/after-tool-call.js:217)工具运行时{target}——kind 仍记 internal,由考官按名单另眼看待
spawn派生子任务工具运行时{label}

家族三 · 平台服务 FC(agent → 平台,不跨 agent,均缓建)

形态是 FC、注册机制与协作工具相同,但对话对象是平台自己——不经 consume 协作管线、不查 role-policy 图边。正确性上系统不依赖它们,各自有明确的「等什么再开」。

例走 · 理想系统

同样两个例子,在设计落地后的系统里重走一遍。先看主体分工的变与不变——写 contract 的永远是平台(这条不变);变的是:期望的翻译有了主体(派工方 LLM,一次、在源头),记账有了主体(证据桥),审判有了主体(考官纯代码),而被审的主体依旧是各环节的 assignee。

职责主体发生在与当前的差异
翻译期望(自然语言→结构)派工方 LLMT0 · assign_task 填参数时新增——FC 本质就是 LLM 填 schema,翻译一次在源头,由当事人做
写 contract(含期望字段)平台(consume→ingress)T0 · 受理之后不变——agent 依旧从不持笔,期望从 FC 参数抄进 contract
记账(实然)证据桥T1 · 每次 tool call新增——两类 FC 同账,被拒调用也记
被审assignee(worker 等)各自会话不变——但判定从「考古猜」变「对账看」
审判考官(纯代码)T3 · 轮次新增——diff(期望, 账本),三态判决,可重放

例一(简单)· 理想走法

用户对 bridge 说:「分析 Q3 销售数据,产出报告,写完让 controller 审一下。」——理想形态下,这句话先到编排者(controller LLM)手里。

1
controller(LLM)翻译期望——协作 FC 派工

controller 理解用户意图后调用 assign_task(协作 FC)。「写完让我审」在此刻被 LLM 翻译成机器可查的期望字段——这是 FC 的本职:把意图填进 schema。翻译一次、在源头、由当事人做,之后全程零翻译。

assign_task({
  "target": "worker",
  "task": "分析 Q3 销售数据,产出报告,写完让 controller 审一下",
  "expectations": {
    "requiredArtifacts": [{ "path": "TC-….md" }],
    "expectedActions": [{ "intent": "wake_agent", "target": "controller", "required": true }]
  }
})  → tool_result 立即返回受理凭证 {accepted, contractId, queuePosition}
✓ 受理时刻校验(治问题②③):平台在受理时就查 schema、role-policy、图边——若 worker 无权 wake controller 或图上无边,返回的是结构化拒绝,controller 当场看到、当场改道(比如改用固定评审边,或申请 operator 修授权),而不是把注定失败的要求塞进任务里。
2
平台写 contract(不变的持笔人)+ 期望入档

consume handler 受理后,平台建 contract——与今天完全同一支笔,只是多抄一个字段:

{
  "id": "TC-1784730001234",
  "task": "分析 Q3 销售数据,产出报告,写完让 controller 审一下",
  "assignee": "worker", "output": "…/TC-1784730001234.md",
  "expectations": {                       ← 三部曲补齐的第三块
    "requiredArtifacts": [{ "path": "TC-….md" }],
    "expectedActions": [{ "intent": "wake_agent", "target": "controller", "required": true }]
  }, …
}

单一真源三处消费:①渲染进 worker 的任务简报(与审计判据不可能分叉)②受理校验已做③留给 T3 考官对账。

3
worker(LLM) + 证据桥干活全程记账;协作动作是真 tool call

read → write → 会话中途直接调 wake_agent(controller)(不再是死后才被翻的便条)。桥在每次调用后照单记账:

{"seq":0,"kind":"session_open","contractId":"TC-…","traceVersion":1}
{"seq":1,"kind":"internal","channel":"fc","name":"read","args":{"path":"sales.csv","bytes":52340},"outcome":"ok"}
{"seq":2,"kind":"internal","channel":"fc","name":"write","args":{"path":"TC-….md","bytes":18234,"hash":"9f2c…"},"outcome":"ok"}
{"seq":3,"kind":"collab","channel":"fc","name":"wake_agent","args":{"target":"controller"},"result":{"accepted":true,"ticket":"SA-…"},"outcome":"ok"}
{"seq":4,"kind":"session_close","eventCount":4}
✓ 治问题②的另一半:就算这次调用被授权拒绝,也会以 outcome:"refused" 入账——worker 生前即知、账上有痕、考官可见「期望与授权冲突」,矛头指向派工配置而不是冤枉 worker。
4
agent_end终态链读账,不再失明

终态链从本会话 trace 过滤 kind:collab 拿到 wake 的受理记录与票据 ID,拿 ID 查票据账取现状,合流进原有终态优先级链。trace 不完整?退回今天的行为,永不崩。

5
考官(纯代码)T3 对账,三态判决

diff(expectations, trace):report.md → seq 2 目击诞生+hash 可复核 → fulfilled;wake→controller → seq 3 受理凭证 → fulfilled。判决写进 EvaluationResult(不再是转贴),automation 的连胜与信任阶梯第一次吃到真数据。若桥当轮抖过(哨兵/seq 校验不过)→ 相关期望判 not_provable,证据不足永不判违约。

例二(复杂)· 理想走法

researcher1 派工:「整理竞品定价数据;若发现异常价格,请 reviewer1 核查;完成后写汇总报告,并叫醒我进下一轮。」

1
researcher1(LLM)条件期望有了安放处
assign_task({
  "target": "worker3",
  "task": "整理竞品定价数据;若发现异常价格,请 reviewer1 核查;完成后写汇总报告并叫醒我",
  "expectations": {
    "requiredArtifacts": [{ "path": "pricing-summary.md" }],
    "expectedActions": [
      { "intent": "request_review", "target": "reviewer1", "required": false },  ← 「若发现异常」= 可选期望
      { "intent": "wake_agent", "target": "researcher1", "required": true }
    ]
  }
})

条件性到 required:false 为止,不做条件 DSL——判断「有没有异常」是 LLM 的内容工作,判断「做没做」才是代码的审计工作,边界不越。

2
worker3(LLM)双动作不再互相残杀

发现异常 → 会话中先调 request_review(reviewer1) 拿受理凭证,继续写汇总,再调 wake_agent(researcher1) 拿第二张凭证。两次独立 tool call,各自受理、各自入账——「只取第一张便条」在表达层彻底消失(contract 的 systemAction 单槽容器数组化仍是 P3 必做的配套)。

3
deferred 回流照旧走票据,但先验过再依赖

review 结果照现有链路回流(票据→评审 agent_end 回投→精确会话唤醒)。设计修订已记档:followUpLease 簿记已死,P3 开工前必须实测这条回流链,不能拿「现有回流」当既成事实。

4
考官三态判决怎么判这一轮

pricing-summary.md 目击+hash → fulfilled;wake→researcher1 有凭证 → fulfilled;review 是 optional:发生了 → fulfilled,没发生 → 不亮红(不知道有没有异常,这不是代码该猜的)。若这轮桥丢过账 → not_provable,worker3 不背锅,「证据不足反复出现」作为系统健康信号盯桥去。

投递载荷显微镜 · 每一跳到底送了什么

把「派工投递」拆到载荷级:每一跳,上家写了什么、系统实际送达什么、接收方看到的指令长什么样、它产出什么。先记住标准载荷四件套——每次投递送到接收方手里的永远是这四样,理想系统在第②样里多渲染一块期望:

#载荷内容关键设计约束
①唤醒指令固定文案「Continue the current contract: TC-…」(动态回流时为 resume 语义唤醒)不含任何任务内容——任务真值永远走文件不走唤醒消息,唤醒只负责「把人叫醒」,防注入面最小化
②inbox/contract.json 投影同一 contract 的 task-facing 白名单裁剪副本:task 原文、output 路径、stagePlan/stageRuntime、assignee、upstreamPackages 指针、(设计新增)expectations投影≠正本:正本永远在 control-plane,agent 只见白名单字段;task 字段全程逐跳不变=用户/派工方原话
③inbox/upstream/<上家>/ 产物包上家全部产物文件+清单(manifest),整包搬运首跳为空;「报告在哪」的答案永远是这里,不在唤醒消息里
④提示词装配SOUL(角色人格)+ 平台把 contract 字段渲染成的开工简报(任务原文/产物要求/阶段/期望动作)接收方看到的「指令」不是上家的原话转发,而是平台渲染的简报;角色分工(你是评审/你是执行者)来自 SOUL,不来自 contract

下面用一条完整管线把四件套装进每个 agent 自己的占位卡里:「用户 → controller(动态派工)→ worker1 →(固定管线交棒)→ worker2」。注意例子的设定:worker1 独自完成全部任务(phases 是它一个人的结构化步骤清单——phase 的本义);worker2 是图上故意留的鲁棒性占位符——下游有个 agent 接到同一句话和一份成品时,系统会怎样?卡内每样东西都标注笔者;卡间的箭头就是平台。

扣点正面回答:worker2 接到的任务是什么?

就是 worker1 那句原话,一字不差,外加一份成品。task 逐跳不变是设计(内容不漂移);而「下游该干什么」的合法来源只有三个——phase 不在其中(phase 是单 agent 内写好 prompt 的工具,拿它做跨 agent 分工是滥用):

来源性质本例
角色分化(SOUL)worker→reviewer 这类异质交接的天然语义worker2 是同质占位,无分化 → 缺位
该跳期望(平台按图/规格导出)结构化,考官可对账(设计新增)图没为 worker2 定义 → 空
动态单腿工单(真要分工就派两张 assign)每张工单 task 即该腿任务,最干净本例未采用(故意)

鲁棒性结论:三个来源全缺位时(正是本例占位测试的设定),worker2 的行为不可预期——复核、重做、空转都可能。系统的正确姿态不是让它猜对,而是不崩 + 不冤 + 不失踪:交棒机械照常工作;考官因期望为空只做产物兜底,不会误判 violated;统一 trace 把它实际做的每一步记在账上,事后一目了然。upstream 里的成品与 replyTo 回传不受影响——占位符最坏也只是浪费一跳,坏不了结果。

⚠ 终审确认点(本节暴露的设计缝):固定管线下同一份 contract 跨多跳,expectations 是按跳的——定为每跳派送时由平台按图/规格为当前 assignee 重导出/覆写;图未定义则该跳期望为空,考官只做产物兜底,不判 violated(动态协作无此问题:每张 assign 工单单跳)。考官按跳对账:该跳的会话 trace ↔ 该跳的期望。stagePlan/stageRuntime 与此无关——它们是单 agent 作用域,不跨跳。这条须在设计终审里正式过一遍。

六个盲区的对照收口

当前盲区理想系统的解
①协作期望无字段expectations 入 contract,单一真源三消费
②授权暗坑(死后拒,无感知)受理时刻结构化拒绝,当场改道;被拒也入账
③意图与拓扑脱节,无人报告受理校验暴露冲突;考官把矛头指向派工配置
④多动作单取,便条蒸发多次独立 FC call 各自凭证(容器数组化=P3 配套)
⑤该叫没叫无人知考官 diff:期望在、账上无 → violated(账不全则 not_provable)
⑥评估空转(转贴)EvaluationResult 吃考官真判决,信任阶梯首次有真依据
