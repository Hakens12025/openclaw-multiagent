# Agent 工作空间 (Agent Workspace)

> 每个 agent 拥有物理隔离的独立目录,它的世界只有 `inbox/` 和 `outbox/` 两个相对路径;系统管的共享区 agent 碰不到。**产物交接是这个空间模型的推论,不是独立系统。**

## 是什么

工作空间是 agent 的**物理边界**。系统里有三类空间,权限截然不同:

| 类别 | 位置 | 谁能写 | 谁能读 |
|---|---|---|---|
| **agent 私有工作区** | `workspaces/<agentId>/` | 该 agent(仅 `outbox/`)+ 平台 | 该 agent(仅 `inbox/`+`outbox/`) |
| **系统共享区** | `control-plane/{contracts,output,artifacts}/` | **只有平台** | **只有平台** |
| **组共享区** | — | **尚不存在**(见 §当前张力) | — |

一个真实工作区的构成(以 `workspaces/worker/` 为例):

```
inbox/          ← 平台投递:contract.json(投影版) + upstream/<producer>/ 上游产物包
outbox/         ← agent 唯一可写处;平台在 agent_end 取件
IDENTITY.md     ← 平台托管(role persona,平台重写)
HEARTBEAT.md    ← 平台托管
SOUL.md         ← 用户拥有,平台永不重写
agent-card.json / deliveries/ / control-plane/   ← 平台管理
```

**关键**:`inbox` 与 `outbox` 之外的一切,agent 都不该碰;`control-plane/` 中央区 agent 连路径都看不到(合约投影按白名单剥离,见 [产物交接](./artifact-handoff.md) 关键设计选择①)。

## 为什么存在

**物理隔离是[核心设计指标](../../use%20guide/)第三条永久原则**(*"不同 Agent 的文件分目录,不共享 workspace"*,明写"不随版本更新而改变")。它同时买到四样东西:

1. **上下文隔离的物理保证** — [上下文隔离](./context-isolation.md)是多 agent 存在的核心理由;目录隔离让它不依赖提示词自觉。
2. **写隔离** — agent A 不可能覆盖 agent B 的产出。这是四条里**最不可让渡**的一条。
3. **可归因** — 每个文件有明确的产出者,`artifacts/<cid>/<producer>/` 的身份模型直接建立在此之上。
4. **传送带成立的前提** — 因为 agent 够不到别处,平台才**必须**负责搬运([传送带原则](./conveyor-belt.md));反过来,agent 也因此不必知道下游是谁。

### 产物交接是推论,不是独立系统

> **因为工作区是隔离的,所以产物必须被搬运。**

如果 agent 共享目录,"交接"就退化成"导航" —— 不需要拷贝、不需要 manifest、不需要指针。整套 [产物交接](./artifact-handoff.md) 机制(采集/整包留存/流转/取件条)**全部是隔离模型的成本**。

这也是判断交接类改动的标尺:**任何交接方案,先问它是否动摇了空间模型。**

## 当前张力(未决)

### 张力一 · 搬运成本 vs 隔离

**问题**(2026-08-06 提出):大量小文件、或单个超大文件(GB 级数据表),在每个 agent 的私有路径之间**逐字节拷贝**,成本很差 —— 同一份 GB 会同时存在于 `artifacts/` 与每个下游 inbox,且每跳重拷一次。

**关键区分**(不要混为一谈):

| 真实需求 | 方案 | 是否动摇隔离 |
|---|---|---|
| 大文件/多小文件不要来回拷 | **硬链接**(已验证 `control-plane` 与 `workspaces` 同属一个文件系统) | ❌ **不动摇** |
| 多 agent 在同一目录**协作写** | 共享可写工作区 | ⚠️ **推翻永久原则三** |

**硬链接为什么不动摇隔离**:硬链接在目标路径上**就是一个真实文件**(同 inode,零字节拷贝)。agent 看到的仍是 `inbox/upstream/planner/big.csv` 这个自己工作区内的相对路径;读白名单做路径解析时得到的也是这个 inbox 路径,**不会像软链那样解析到白名单之外被拒**。语义完全不变,只是字节不再复制。
⚠️ 限制:仅限同一文件系统(已满足)、仅限文件不能链目录、源删除后链接仍存活(对不可变产物反而是优点)。

**所以性能问题可以在不碰隔离原则的前提下解决。** 只有"多 agent 同时在一个目录里写"才是真正需要推翻原则的那件事。

### 张力二 · AgentGroup 名不副实

[AgentGroup](./agent-group.md) 被定义为**空间原语**(当年与 Loop 的时间原语正交;Loop 已于 2026-08-18 退役),但 `GroupSpec` 的字段是 `{id, members, entry, internalEdges, outputMode, metadata}` —— **全是拓扑,没有任何空间(目录)维度**。

若将来确实需要"面向部分 agent 的共享工作区",**AgentGroup 是唯一有原则的作用域**:组即共享边界,组内共享、组外隔离,而不是开一个全局共享目录。那样也会让"空间原语"这个名字第一次名副其实。

**但这需要显式推翻永久原则三,不能默默做。** 需要回答的问题:
- 共享的是**读**还是**写**?(读共享今天已经通过拷贝实现了,硬链接只是换实现;写共享才是新能力)
- 写冲突怎么办?(两个 agent 同时改同一文件)
- 归因怎么办?(`artifacts/<cid>/<producer>/` 的 producer 身份从哪来)
- 组解散后目录归谁清?(参见 [产物交接](./artifact-handoff.md) 的「谁写谁清」缺位)

## 和谁交互

- [产物交接](./artifact-handoff.md) — 隔离模型的直接推论:因为隔离所以要搬运

- [传送带原则](./conveyor-belt.md) — agent 只读 inbox/写 outbox,平台负责搬运
- [AgentGroup](./agent-group.md) — 若引入组共享工作区,它是唯一有原则的作用域

## 当前状态

**稳定(隔离模型) / 有未决张力(搬运成本与组共享)**。隔离本身是永久原则,不在讨论范围;待决的是①是否用硬链接把搬运成本降到零(不动原则,可做)②是否引入 AgentGroup 作用域的共享可写工作区(**动原则,需显式决策**)。
