# 平台/Agent 解耦

> agent 是平台上生存的物种。平台提供工具和地图,不要求 agent 内部有特定逻辑——平台为 agent 提供服务,不是 agent 的衍生品。

## 是什么

一条可检验的判据:**把一个从没读过 OpenClaw 文档的 agent 放进来,它能干活吗?**

判据把"平台要求 agent 事先知道什么"变成可以逐条清点的东西。每一条私有协议都是耦合:

| 协议 | 谁教 | 不遵守的后果 | 现状 |
|---|---|---|---|
| 产物放进 `outbox/` | 提示词 | 平台看不见 | 仍是约定 |
| 写 `outbox/runtime_result.json` | 提示词 | **曾经:产出全部不被采集** | v179 起降为可选 |
| 文本标记语法 | 拒绝信息 | 协作动作丢失 | 降级路,不进主提示词 |

**解耦形态与耦合形态的对照**(同一件事):

| | 耦合 | 解耦 |
|---|---|---|
| 协作 | 要知道 `[ACTION]` 语法、写在产物末尾、还得附在正文之后 | **调 `assign_task` 工具** |
| 先验知识 | 必须读过文档 | 零——工具带 name/description/schema 自描述 |
| 出错反馈 | 下一轮才知道 | **调用当场结构化拒绝** |

## 为什么存在

**耦合的代价是静默失败。** live 实测两例:

- agent 写对了正文、写对了 `[ACTION]` 标记、干完了活,只因没额外写 `runtime_result.json`,平台判定它什么都没交 —— 标记随文件一起消失,连告警都没有
- agent 拿到 `inbox/upstream/<producer>/` 却没有列目录的手段,连着猜四次文件名全落空,还拿 `read` 读目录得到 `EISDIR`

两例的共同结构:**平台知道答案却不说,或者要求 agent 先学会一件平台自己就能做的事。**

反向证据同样有力:FC 工具被故意堵死后,planner **从拒绝信息里现学**降级写法,一次写对——它没读过任何降级教程(那部分刻意不在提示词里)。**平台在需要的时刻把知识递过去,比要求 agent 事先背下来更可靠。**
