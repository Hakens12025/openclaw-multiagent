# 产物交接 (Artifact Handoff)

> agent 是一间只有收件箱和发件箱的办公室,平台是收发室:产物永远在磁盘上按生产者整箱流转、永远不进提示词,送到留取件条、送不全留缺料条。

> ⬆️ **父概念**:[Agent 工作空间](./agent-workspace.md)。**产物交接是空间隔离模型的推论,不是独立系统** —— 因为每个 agent 的工作区物理隔离,产物才必须被搬运;若 agent 共享目录,"交接"会退化成"导航"。判断任何交接类改动,先问它是否动摇了空间模型。

## 是什么

产物交接是「上一个工位的成果如何成为下一个工位的输入」这套机制。它不是独立设计的子系统,而是[Agent 工作空间](./agent-workspace.md)的物理隔离,叠加[硬路径与软路径](./hard-soft-path.md)、[传送带原则](./conveyor-belt.md)、[graph edge = 固定管线与投递路径](./graph-edge.md)三条第一原则在**数据维度**的必然推论。

链路五步(代码真值见 §关键实现):

```
agent 写 outbox/ → ①采集 → ②整包留存 → ③流转下游 → ④判定 → ⑤回传
                              artifacts/     inbox/upstream/  证据判定  delivery
```

第③步是 **pull 不是 push**:平台把箱子送到门口,并在合约里放一张取件条(`upstreamPackages`),agent 自己去读。
取件条**带清单**——每条是 `{path, producer, files[], primary}`,清单在拷贝时 readdir 顺手产出。此前它只给目录路径,而下游手里只有 `read`(要确定路径),拿到目录名等于没有入口(live 实测连猜四次文件名 + 一次 `EISDIR`)。第⑤步属于[投递 (Delivery)](./delivery.md),不在本页范围。

整包流转的决策细节见 [产物整包流转](../decisions/artifact-package-flow.md)。本页记录**整套机制赖以成立的不变式**。

## 为什么存在

### 七条不变式

所有代码都在维护下面七条。它们互相咬合,拆掉任何一条其余都会松动。

| # | 不变式 | 为什么 |
|---|---|---|
| 1 | agent 的世界只有 `inbox/` 和 `outbox/`,只用相对路径 | 绝对路径 = agent 感知了大楼结构 = 沙箱破了 |
| 2 | agent 不知道下游是谁 | 硬编码 agent 名会让拓扑不可改;改图必须安全 |
| 3 | 平台搬运,agent 只管内容 | 第一原则的直接落地 |
| 4 | 产物必须有文件系统证据才算完成 | 防止 agent 自我宣告成功 |
| 5 | 下游必须知道自己缺了什么 | 静默缺失比明确缺失危险得多 |
| 6 | 产物子系统绝不打断主链 | 产物是增强,不是命脉 |
| 7 | 留存严格早于派工 | 下游被唤醒时上游的包必须已在盘上 |

**自洽链**:因为 agent 只有两个面(1),平台必须搬运(3);因为平台搬运,agent 不必知道下游(2);因为不知道下游,拓扑才能随便改;因为产物在磁盘不在上下文,才能整包流转而不炸上下文;因为完成看盘上证据(4),采集才必须可靠;因为缺料必须可见(5),溢出才降级而不丢弃;因为产物不能拖垮主链(6),留存才吞错;因为留存吞错,阶段序(7)才必须由代码保证而非靠错误传播。

### 五个关键设计选择

整包流转与「产物不进提示词」两项见 [产物整包流转](../decisions/artifact-package-flow.md)。以下五项此前未成文:

**① `contract.output` 对 agent 不可见** — 合约投影进 inbox 时按白名单剥掉 `output` 字段。理由是事故驱动:*"output 与 outbox 易混,曾有 agent 把 output 误当写入路径"*(代码注释原文),agent 一旦直写中央路径就绕过了整个采集流程。**拒绝了**靠提示词教育 agent 别写那个路径——软约束治不了这种事。判定侧再从共享合约把 output 补回来,这也是 v133 mirror bug 的修复形态,不可回退。

**② 有界注入 + 降级而非丢弃** — ⚠️ **本条已被决策推翻,待实现下线**(2026-08-06,源: 备忘录130 §十)。原设计:上游产物灌进下游 inbox 有跨 producer 共享字节池,装不下降级成 `COMPRESSED_MANIFEST.md`,拷贝失败落可见的 `_MISSING.md`。

**推翻理由**:它把「搬运字节」与「上下文字节」当成同一个量。产物是**文件**、agent 是**按需 Read**,两者无函数关系 —— 几个 G 的数据表必须搬,但下游可能一个字节都不读进上下文。实测真实 agent 产物 p99 仅 15.3KB、峰值 19.4KB,**预算比史上最大负载大 60 倍且从未触发**(两条分支 817 次注入 0 命中)。更关键的是 `_MISSING.md` **违反第一原则** —— 它把一次拷贝失败写成自然语言交给 LLM 决策,让软路径去处理硬路径的失败。

**替代设计(纯框架,零 LLM 参与)**:枚举 → 拷贝 → **对 manifest 自查(数量+大小)** → 齐则写指针(**指针即已验证送达的回执**)、缺则重拷、超限仍缺则框架级错误并**阻止派工**。不变式 5 由此改为由**代码保证**而非由 marker 告知 LLM;同时不变式 6 需拆细为「生产侧失败不打断主链 / 消费侧注入失败应阻止派工」。上下文保护若将来需要,归**读取工具层**,不归搬运层。

**③ 完成 = 文件系统证据,不是自我宣告** — agent 写的 `runtime_result.json` 里 `status: completed` **不算数**,判定必须看到真实产物文件。这是整个门控最重要的一条:LLM 会宣称自己完成了,唯一可信的是盘上有没有东西。有测试钉死"runtime 说完成 + artifacts 为空 → FAILED"。

**这条不变式反过来也说明该文件不该是采集的前提**:既然 `completed` 本就不被信任,要求它在场才肯采集就只是把平台的记账义务外包给 agent。v179 起采集无条件进行,该文件降为降级路——它真正承重的只有 `status: failed / awaiting_input / hold`(那是平台不可知的声明),其余字段平台自己都有兜底。

**④ 产物子系统吞错不抛** — 留存失败静默处理,绝不让 agent_end 挂掉(代码两处注释写死此红线)。理由是不变式 6:产物存不下是遗憾,因为存不下让整条链崩掉是灾难。**代价是有意识认下的**——换来生产侧观测不足,该补的是日志而非抛错。

**⑤ 不造第二条搬运协议** — 已退役的评审腿(request_review)当年把产物送给评审方时复用同一个 `copyUpstreamArtifactsToInbox`,只是先把包物化到新合约名下,预算/溢出清单/缺料标记全套照常生效。理由是一条路径原则:两套搬运机制 = 两套 bug + 两套语义 + 永远对不齐。

### 两个平面共用同一套产物语义

|  | 固定管线 | 动态派工 |
|---|---|---|
| 拓扑 | 预先声明的 graph 边 | 运行时生成的子合约 |
| 触发 | agent 结束后按出边路由 | agent 产出里发起 `assign_task` |
| 语义 | 这条链一直这么走 | 这一次我需要谁帮个忙 |

**设计意图是两者共用同一套产物机制**,动态腿不该有自己的搬运方式,只是"把包按新合约名上车"。规格里从没写过"动态派工不带产物"——assign 腿目前的零产物交接是**实现缺口,不是设计**(源: 备忘录129 §二、备忘录130 §四)。

### 刻意不做的事

- 不把产物塞进上下文——磁盘承载数据,上下文承载指令
- 不假设一个 agent 只产一个交付物
- 不信任 agent 的自我宣告
- 不在路由里硬编码 agent 名
- 不让 agent 感知中央存储
- 不造第二条搬运路径
- 不让产物故障传染主链
- 不用 edge 表达时序
